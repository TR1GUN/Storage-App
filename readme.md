# Сервис для хранения данных.
Данный репозиторий, представляет собой альтернативный вариант приложений, представленное в [другом репозитории](https://github.com/TR1GUN/Storage-Servises).

Главное отличие от другой реализации - переход на Go в качестве языка реализации, для того чтоб реализовать условия задачи по минимальному количеству зависимостей, но при этом не жертвовать производительностью.

# Вспомним условия:
есть задание, которое условно сделал бизнес-аналитик:
```
Написать простейший HTTP сервер, который принимает запросы на:

- выдачу записи по уникальному идентификатору

- уникальный идентификатор

Пожелания:
```

# Системная аналитика
Архитектурно понятно что из себя будет представлять приложение

У нас есть простейший сервер, который будет иметь 3 ручки.
Для простоты будет использоваться Rest.
- GET запрос для получения всех записей `/records`
- GET запрос для получения определенной записи `/records/{id_records}`
- POST запрос для сохранения записи `/records` использованием идентификатора, который есть в самой записи.

Хотя формулировка `"Между запусками сервер должен сохранять все ранее созданные записи."` прямо противоречит пункту `"- сохранение записи"`.
введем допущение, что при REST запросе и при запуске сервера мы сохраняем разными способами и в разные места.

Поскольку есть пункт `"Использовать готовые базы данных нельзя."`, который мы можем интерпретировать как прямой запрет
использования всех систем хранения данных: как SQL, так и NoSQL, необходимы альтернативные виды хранения данных.

### Схема работы: ###

У нас есть 2 области хранения:
- Зона временного хранения
- Зона долгосрочного хранения

Временное хранение представлено в виде 1 файла, который имеет свой путь и задается через .env
При получении данных через HTTP запрос, сохранение идет во временное хранилище в виде файла JSON
В котором структура представлена в виде записей:

`ID записи : Запись`

В качестве записи мы берем данные из JSON тела HTTP запроса по ключу "record"
В качестве ID мы берем данные из JSON тела HTTP запроса по ключу "idx"

Для быстроты работы, все ID из этого файла мы так же храним в памяти приложения.

Зона долговременного хранения представляет собой директорию в которой лежат
наши записи в виде отдельных JSON файлов и файл их учета:
Путь директории, имя файла учета и шаблон имен отдельных JSON файлов задается через .env

Структура файла учета
`ID записи : Имя файла`

Структура JSON файла
```
record:Запись,
idx: ID записи
```
Имя файла формируется по форме `Шаблон_имени_$его_ID`.

При старте приложения, все записи из Зоны временного хранения
записываются в отдельные файлы в зоне долгосрочного хранения

Правила формирование ID

- ID Задается пользователем.
- Если ID совпадает с тем что уже есть - Данные перезаписываются.

Получение файлов по ID работает по принципу:
1) Ищем нужный индекс в файле временного хранилища,
2) Ищем нужный индекс в файле долгосрочного хранилища
3) Если индекс не найден, то считаем что такого файла нет.

При отдаче всех записей. сервис отдает все записи: Что находятся и во временном и в долгосрочном хранилище
- Имеет ли смысл разделить ручки получения всех записей ?

# Реализация
Напомним, какая структура проекта была определена:

У нас есть 3 метода:
- Добавление данных
- Получение данных
- Получение всех данных

У нас есть 2 сущности:
- Временное Хранилище - HotStorage
- Постоянное Хранилище - ColdStorage

Классический CQRS - Command Query Responsibility Segregation.

Поскольку у нас есть требование по нагрузке, то стоит разделить 2 типа операции.
- Чтение
- Запись

Запись у нас осуществляется в 2 Этапа:
- Первичная запись в HotStorage
- Миграция данных в ColdStorage

Чтение осуществляется в один этап, но он разделен на 2 хранилища.
- Поэтому имеем смысл хранить ссылки на место где находится объект в HotStorage, чтоб быстро иметь доступ к этому участку файла
- Для быстрого доступа к ColdStorage, имеет смысл индексировать в отдельном файле все записанные пути файлов, чтоб быстро искать нужный файл. Назовем его файл индексации.
    - При создании Это пустой JSON
    - Если записи нет в файле индексации, то считаем что такой записи нет.

Миграция данных:
- При миграции файл читается весь файл HotStorage.
- Во временное хранилище записываются данные из HotStorage в отдельные файлы ColdStorage.
- Пути всех файлов записываются в отдельный файл индексации ColdStorage.

т.е. Общий алгоритм и жизненный цикл программы:
- Старт приложения ->
- Создаем необходимые файлы ->
- Миграция данных в Долговременное хранилище полученных данных из Временного хранилища до этого ->
- Записываем во временное хранилище ->
- Перезапускаем приложение по истечении временого цикла.

## Архитектура

### Hot Storage (Горячее)
- Формат: JSONL (JSON Lines) — по строке на запись
- Индексы в памяти: `map[int]PositionToFile`
- Быстрая запись, данные хранятся до перезапуска

### Cold Storage (Холодное)
- Формат: отдельные JSON файлы в директории
- Индексный файл: пути ко всем файлам записей
- Миграция из Hot при старте приложения

## Жизненный цикл
1. Старт → создание файлов
2. Миграция Hot → Cold
3. HTTP запросы → запись в Hot
4. Перезапуск → миграция накопленных данных в Cold

# Производительность

## Метрики

Бенчмарк запускается через `./run_benchmark.sh` или `docker run benchmark`.

| Метрика | Описание |
|---------|----------|
| **Save** | Конкурентная запись N записей (горутин) |
| **Get** | Конкурентное чтение N записей по ID |
| **List** | Получение всех записей |
| **Throughput** | Запросов в секунду |

## Ожидаемые результаты

| Версия | Save 200 | Get 100 | List | Throughput |
|--------|----------|---------|------|------------|
| Go (std) | ~0.1-0.3s | ~0.05-0.15s | ~0.01-0.05s | 500-2000 req/s |

## Сравнение с другими реализациями

| Версия | Язык | Зависимости | Save 200 | Get 100 |
|--------|------|-------------|----------|---------|
| Go (Pure stdlib) | Go 1.24 | 0 | ~0.1-0.3s | ~0.05-0.15s |
| FastAPI | Python 3.14 | uvicorn, fastapi, pydantic | ~0.2-0.5s | ~0.1-0.3s |
| Aiohttp | Python 3.14 | aiohttp, aiofiles | ~0.3-0.6s | ~0.15-0.4s |

## Почему Go быстрее

1. **Компиляция в нативный код** — нет VM/интерпретатора
2. **Горутины** — лёгкие конкурентные потоки (vs asyncio event loop)
3. **Нулевые зависимости** — нет накладных расходов сериализации (pydantic)
4. **GC оптимизирован** под low-latency — меньше pause times
5. **Стандартная библиотека** — `encoding/json` написан на Go, без Python overhead
